# Project quality baseline

Goal: a project has, from the start, linting, strict typing, unit tests, optional CI, commit conventions and an up-to-date CLAUDE.md. Work step by step and show what is being done.

## 1. Survey (change nothing)
- Identify the stack: `package.json`, `nuxt.config.*`, `vite.config.*`, `composer.json`, `artisan`, `docker-compose.yml`.
- Package manager: `package-lock.json`, `pnpm-lock.yaml` or `yarn.lock`. Use the project's one.
- What already exists: ESLint/Prettier config, `tsconfig.json`, tests, `.github/workflows/`, `CLAUDE.md`, Git hooks, commitlint.
- Present a short summary: what is in place, what is missing, what will be proposed.

## 2. Questions (once, grouped)
Ask with AskUserQuestion if available, otherwise in text:
1. **GitHub Actions CI**: run lint, typecheck and unit tests on every push and pull request? (yes / no / later)
2. **E2E tests in CI**: add them now, later, or not at all? (rely on the `e2e-tests` skill if yes)
3. **Pre-commit checks** (Husky + lint-staged): yes or no?
4. **Commit message check** (commitlint with Conventional Commits, see the `conventional-commits` skill): yes or no?
5. **Languages**:
   - content language(s) of the site or app, i.e. everything the end user sees or hears (UI text, `alt`, `aria-label`, error messages, SEO metadata, emails). If several languages: is an i18n setup expected (for example `@nuxtjs/i18n`)? Do not install it unless asked;
   - language of code comments and documentation (English by default, unless the agency or client imposes another).
   Code identifiers and commit messages stay in English unless the repository's conventions say otherwise.
6. **Performance budgets** (recommended for long-lived projects and anything with 3D): asset budget, JS bundle budget, 3D leak test, Lighthouse CI as a warning (see "Regression guards" in the `performance-memory` skill). For a short campaign, usually not worth it. Thresholds for the asset budget: textures 2048 or 1024 (mobile, WebAR), USDZ required or not.
7. **Agency or client repository**: are there imposed conventions to follow? If so, they take priority.
Do not ask a question whose answer is obvious from the project.

## 3. Linting and formatting
- **Nuxt**: `@nuxt/eslint` (flat config `eslint.config.mjs` generated by the module).
- **Vue/Vite or vanilla JS/TS**: ESLint flat config with `typescript-eslint` (and `eslint-plugin-vue` for Vue).
- **Prettier** or formatting through ESLint Stylistic: pick one, never two conflicting formatters (`eslint-config-prettier` if Prettier).
- **Laravel**: Laravel Pint for PHP, PHPStan/Larastan (level 5 to start, raise it later).
- Add `eslint-plugin-vuejs-accessibility` on Vue projects (consistent with the `accessibility` skill).
- Scripts: `lint`, `lint:fix`, `format`.
- Run `lint:fix` once and report what is left to fix by hand, without disabling any rule to make lint pass.

## 4. Strict TypeScript
- `"strict": true`, plus `"noUncheckedIndexedAccess": true` and `"noImplicitOverride": true`.
- Nuxt: options in `nuxt.config` (`typescript.strict`, `typescript.tsConfig`), checked with `nuxi typecheck` (install `vue-tsc` if Nuxt asks for it).
- Vue/Vite: `vue-tsc --noEmit`. Vanilla TS: `tsc --noEmit`.
- `typecheck` script.
- Existing project with many errors: do not fix everything at once nor weaken the config. Propose enabling `strict` and fixing in batches, or list the errors for a decision.

## 5. Unit tests
- **Vitest** for Nuxt, Vue, Vite and vanilla JS (`@nuxt/test-utils` for Nuxt, `@vue/test-utils` for components, `happy-dom` environment).
- **Pest** (or PHPUnit if already present) for Laravel.
- Write a first real test on an existing function of the project, not an empty `1 + 1` test.
- Scripts: `test` (single run, for CI) and `test:watch`.
- Coverage available (`test:coverage`) with no blocking threshold at first.

## 6. GitHub Actions CI (if approved in step 2)
File `.github/workflows/ci.yml`:
- Triggers: `push` and `pull_request`.
- Jobs: install (`npm ci` or equivalent, with cache), `lint`, `typecheck`, `test`. Add the e2e job if requested, following the `e2e-tests` skill.
- `permissions: contents: read`, actions pinned to a major version, `concurrency` to cancel outdated runs on the same branch.
- Node version read from `.nvmrc` or `engines` (create `.nvmrc` if missing).
- Laravel: PHP job with `composer install`, Pint in test mode, PHPStan, Pest.
- Performance budgets, if approved: after the build, `node scripts/check-assets.mjs` and Size Limit (blocking); the leak test runs with the e2e tests; Lighthouse CI in a separate job that never blocks the merge.

## 7. Git hooks (if approved)
- Husky + lint-staged: lint and format staged files only. Typecheck and tests stay in CI to keep commits fast.
- commitlint with `@commitlint/config-conventional` on the `commit-msg` hook, if approved.

## 8. Project CLAUDE.md
Create or complete `CLAUDE.md` at the root from this skill's `CLAUDE-template.md`. Fill in the project's real commands and the "Languages" section with the answers from step 2, remove irrelevant sections. If a CLAUDE.md exists, add only what is missing.

## 9. Final check
- Run `lint`, `typecheck` and `test`: everything must pass, or remaining issues must be listed.
- Summary: files created or changed, packages added, available commands, what is left to do.
- Do not commit without approval. When approved, use a Conventional Commit (for example `chore: set up linting, strict typing and unit tests`).

## General rules
- Versions: install current package versions and check the documentation (Context7 if available) rather than writing configs from memory, as ESLint and Nuxt config formats have changed in recent years.
- Stay minimal: only add the tools listed here or requested (see the `code-simplicity` skill).
- Never disable a rule or weaken typing to make a check pass without saying so.
